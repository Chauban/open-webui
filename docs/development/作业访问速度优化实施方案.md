# 作业访问速度优化实施方案

> 编写日期：2026-11-12（北京时间）。
> 状态：本地实现、回归和隔离性能验收完成（2026-11-12）。本轮未部署南科大或哈工深。结果、限制与具体发布清单见第 12 节。
> 本地核对基线：`main`，HEAD 为 `afc653da5`（`docs: 记录南科大备份预演与升级验收`），另有未提交和未跟踪文件。该 HEAD 不代表线上版本，也不包含全部现有优化。
> 范围：学生“我的作业／写作首页”与作业写作工作区的访问、返回及再次进入。先解决已测瓶颈，再按证据扩大范围。

接手入口：[给下一个 AI 的提示词](作业访问速度优化AI接手提示词.md)。本文件是该优化方案的唯一维护版本，不在仓库外层另建副本。

## 1. 要解决的问题

学生点击“我的作业”后等待列表；点击“继续写作”后又等待工作区。即使几秒前刚访问过，再次进入仍需等待。此前本地还出现过“空对话／AI 正在阅读遮罩 → 转圈 → 原稿与原对话”的中间画面。

本次目标是缩短真实的可用时间，同时完整恢复服务器稿件、对话、未发送输入与正常权限状态。骨架屏、缓存预览和提前关闭转圈都不能代替真正恢复完成。

优先顺序：

1. 核对并保留工作区已有优化，补齐遗漏和竞态。
2. 减少进入作业时必须串行等待的网络往返。
3. 安全改善短时间返回列表的体验，合并重复刷新。
4. 对查询、响应体、聊天渲染和资源加载做有测量依据的优化。
5. 在真实长稿、历史对话与状态变更场景下验收；获授权后分别发布并复测两个实例。

不把本任务扩展成模型生成加速、数据库迁移、画像重算、历史数据修复、前端框架替换或未经授权的生产部署。

性能优化不得改变以下规则：

- 教学身份、班籍、资源归属、作业隐藏与个人写作开关继续由服务器校验。
- 当前产品规则允许超过截止继续写作和提交；已批改定稿仍只读。线上旧版本的截止行为不能反向成为新实现的依据。
- 真正进行中的初读、复看或聊天生成仍按现有规则锁定编辑／提交；单纯恢复页面不能冒充 AI 正在阅读。
- 已完成或失败的初读在重入时恢复原状，不自动重发、不新建第二条修订对话。
- 本地未同步稿件仍由学生确认恢复；不自动覆盖服务器稿件，不跨账号读取备份。
- 历史提交、评分、来源稿件与调用证据保持冻结；不为了少读数据而用当前稿替代历史快照。
- 不增加历史坏数据兼容分支、运行时补建或自动回填。缺失资源按当前明确错误边界处理。

## 3. 已有测量证据

### 3.1 线上连续往返三轮

站点：[南科大实例](https://rightwrite.cc/me/writing)、[哈工深实例](https://hitsz.rightwrite.cc/me/writing)。

方法：同一台电脑、Tabbit 浏览器、现有已登录测试账号，各选一份已经访问过的作业，连续返回首页再点击“继续写作”。从页面实际收到点击事件开始计时，到列表或对应稿件区域恢复完成为止；不把自动化命令的执行开销计入。

| 实例与操作             | 第 1 轮 | 第 2 轮 | 第 3 轮 | 三轮平均 |
| ---------------------- | ------: | ------: | ------: | -------: |
| 南科大：返回“我的作业” |  444 ms |  437 ms |  451 ms |   444 ms |
| 南科大：进入同一作业   | 2009 ms | 1995 ms | 2021 ms |  2008 ms |
| 哈工深：返回“写作”首页 |  456 ms |  461 ms |  461 ms |   459 ms |
| 哈工深：进入同一作业   | 1647 ms | 1699 ms | 1682 ms |  1676 ms |

这三轮均未发生整页刷新，也未捕获页面脚本错误。再次进入没有明显变快。

**测量边界：**

- 南科大样本为未确认初稿的空稿工作区；哈工深样本为旧版本下已截止、只读的空稿工作区。
- 两个样本都没有历史对话；不能据此声称长稿、图片或完整聊天记录恢复已经验证。
- 哈工深返回首页后，先展开“已截止未交”分组，再对“继续写作”的实际点击计时；展开分组不计入进入作业的耗时。
- 这是当前网络下的三轮已访问页面测量，不是冷启动测试、并发压测或 P95 统计。
- 未修改稿件、发送 AI 消息或提交作业。导航本身会触发应用既有的通知已读和设置保存请求。
- 本次未记录两个站点的精确构建哈希。接手人须重新核对，不以本地 HEAD 代替线上版本。

### 3.2 请求顺序解释了主要等待

两个实例测得的单次接口往返大多约 380—460 ms，包含浏览器、网络、代理和服务端时间，**不等于后端业务处理耗时**。

进入作业时观察到的关键顺序：

```text
点击继续写作
  → GET assignment workspace
  → POST notifications/mark-read
  → GET notifications/summary
  → GET teaching-summary
  → 工作区挂载
  → 未确认初稿时再 GET pending-draft
  → 稿件可用
```

南科大空稿多出的 `pending-draft` 还要再等一轮网络。已有正文和聊天的场景需要继续测阅读历史、聊天及任务状态，不能用空稿样本替代。

通知已读与角标更新不应成为展示正文的前置条件。按这次往返时间估算，仅把这两个通知请求移出阻塞链路，就可能少等约 0.8 秒；这是推算，必须在目标实例发布后验证。

### 3.3 本地问题与线上问题分开记录

本地曾测到同一个首页接口：经过开发服务器 5050 约 1.2—1.4 秒，直连后端 8080 约 35 毫秒。排查期间还捕获到开发进程大量编译、文件解析和垃圾回收开销。

当前 Vite 默认目标已由 `http://localhost:8080` 改为 `http://127.0.0.1:8080`，并重载了开发服务。稳定后，本地三轮实际点击到内容显示依次为：首页 150／111／98 ms，工作区 228／242／217 ms；稿件、对话和未发送输入核对一致。

这些本地数字仅作诊断证据：

- 改地址与重载服务一起进行了，没有做严格单变量 A/B，不能断言全部延迟由 `localhost` 解析导致。
- 开发服务重载后的首次编译要单独计时，不混进已访问页面的跳转基线。
- Vite 开发代理配置对线上实例没有直接作用，本地百毫秒结果不能作为线上承诺。

## 5. 范围与目标

### 5.1 性能目标是验收门槛，不是当前成绩

在接近本次线上条件、单次请求往返约 400 ms 的环境下，按相同账号、数据规模、网络和完成判据比较：

| 场景                               | 第一阶段目标                                         | 补充要求                                                         |
| ---------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| 首页无缓存、已登录应用内导航       | P50 ≤ 500 ms，P95 ≤ 800 ms                           | 当前基本可用，避免优化后退化                                     |
| 同账号短时返回首页，有合格缓存     | 列表预览 P50 ≤ 150 ms；最新数据另记耗时              | 缓存预览不算新鲜数据校验完成；不满足权限失效条件时不启用内容缓存 |
| 空稿／普通稿工作区，已访问应用资源 | P50 ≤ 1.0 s，P95 ≤ 1.5 s                             | 稿件、适用配置和锁定状态真实恢复；不只是显示壳层                 |
| 约 2 万字、50 条消息的测试工作区   | P50 ≤ 1.5 s，P95 ≤ 2.0 s                             | 编辑器可按正确权限操作，最近对话已恢复；历史均可回看             |
| 所有场景                           | 无错误闪屏、无数据丢失、无重复初读、无新增控制台错误 | 功能正确性优先于秒数                                             |

P50／P95 在本地生产构建或隔离测试环境至少采集 20 次，说明计算方法；三次线上样本只报告逐次值、范围和平均值，不伪造 P95。线上获授权后用少量真实导航核验，不自动进行并发压测。

### 5.2 请求与内容预算

- 首页一次进入最多一个同身份、同参数的在途首页请求；发生真正的新事件可在该请求后补一次刷新。
- 作业初始状态目标为一次主要响应；需要独立加载聊天时，最多增加一批必要请求。不得再串行等待通知、标签、侧栏和装饰性摘要。
- 同一对话历史一次进入原则上只取一次；后续真正新增阅读消息、重连或主动刷新不计为重复。
- 不为减少请求数而把所有历史稿件、原始图片、文件二进制和长消息的重复副本塞进工作区响应。
- 记录压缩后传输体积、解压后的 JSON 体积及解析／编辑器挂载时间，防止“请求更少，响应更重”。

## 6. 实施顺序

### 阶段 A：整理已有优化并补足测量

1. 核对第 4 节现有 diff，明确本轮修改与其他任务的边界；确认缺失的未跟踪文件也在交付范围。
2. 固化四个计时点：实际点击、首个有效内容、业务状态校验完成、稿件与对话可用。缓存预览另设指标。
3. 记录请求开始／结束、请求次数、响应体大小、整页导航、错误及页面销毁后的迟到响应。
4. 对未确认初稿、已确认并有对话、生成中、失败、已批改、被退回分别建立隔离样例。
5. 检查 `getChatLoadState`：标签是辅助数据，移到后台且限制迟到结果只能更新所属对话；历史和真实运行任务状态仍属于正确恢复所需信息。
6. 确认一次进入不因阅读记录变化、活动对话恢复、侧栏订阅、通知角标变化重复装载完整历史。

验收：现有行为回归通过；慢通知或慢标签不阻止已具备必要状态的内容显示；登录失效／权限拒绝仍走真实错误处理。

### 阶段 B：合并工作区必要初始数据（核心）

**推荐扩展当前工作区响应并同步更新消费者，不再叠加一条“先取 workspace，再取 bootstrap”的链路。**

代码起点：

- `backend/open_webui/routers/education.py`：`get_assignment_workspace`、暂存稿、阅读记录和适用试读入口。
- `backend/open_webui/models/education.py`：`AssignmentWorkspaceResponse`、`UnifiedWritingWorkspaceResponse` 及相关模型。
- `backend/open_webui/routers/teaching_trials.py`：学生 `teaching-summary` 入口。
- `backend/open_webui/services/education/`：把可复用的初始数据装配放进业务服务，路由负责授权和响应。
- 前端 `src/lib/apis/education/`、`WritingWorkspaceShell.svelte`、`DraftBaselineStep.svelte`、`Chat.svelte`。

建议契约如下，字段名可在实现时按现有命名统一；这是设计，不代表现有 API 已支持：

| 数据                                                   | 何时需要           | 要求                                                                        |
| ------------------------------------------------------ | ------------------ | --------------------------------------------------------------------------- |
| 作业、会话、服务器当前稿、来源映射、当前评阅和有效截止 | 每次进入           | 继续沿用现有权威数据与权限校验                                              |
| 学生可见的辅导模型／版本摘要                           | 适用作业           | 复用学生摘要，不能返回连接凭据、教师私有准备稿或管理员配置全集              |
| 未确认初稿暂存状态                                     | 尚未确认初稿       | 一并提供完整结构稿、材料元信息及暂存 revision，使编辑器无需挂载后再串行 GET |
| 当前阅读状态、已有初读事实、必要的阅读／聊天关联       | 已确认的修订作业   | 明确 running／ready／failed；不能用缺失字段或请求失败推断“从未初读”         |
| 当前轮试读状态                                         | 从零写作且启用试读 | 未启用时无请求、不启动试读                                                  |
| 活动对话信息及必要的运行状态                           | 有已有对话         | 服务器先确认归属与实际绑定；可以合并，或作为唯一下一批关键请求              |
| 标签、通知角标、侧栏树、过程统计、未展开的原件列表     | 非关键展示         | 后台或按需读取，失败不拖垮已经恢复的工作区                                  |

实现约束：

1. 不在聚合服务里用 HTTP 调用自己的已有路由。抽取／复用服务函数，避免重复鉴权、重复开事务和重复读取。
2. 不用 `asyncio.gather` 让多个协程并发操作同一个 SQLAlchemy Session；数据库会话与事务边界按项目现有机制处理。
3. 当前 workspace GET 可能创建写作资源、恢复项目侧栏可见性。因此禁止在链接悬停、列表批量渲染或无用户进入意图时预取它。
4. 聚合初始读取不得调用模型、创建新的阅读、代发消息或修改历史证据。实际首次确认初稿后的既有初读流程单独保留。
5. 后端访问校验仍为最终边界。进入后教师刚完成批改、隐藏作业或撤销权限，后续写请求也必须即时拒绝。
6. 处理聚合期间状态变化：带上已有的配置版本、暂存 revision、稿件／会话标识，并定义哪些数据为同一读取范围；不把多次读取包装成虚假的数据库一致性快照。
7. `DraftBaselineStep` 接收明确的已加载初始状态；区分“初稿为空”与“尚未加载／加载失败”。不再无条件 onMount 重取相同暂存稿，也不能因此把空文档保存覆盖真实稿。
8. `Chat` 若接收预装载历史，首次只消费一次且核对 chat ID；后续实时消息和任务事件不能被较早的初始响应覆盖。不使用跨账号的全局聊天缓存。
9. 审查现有 `RevisionReading.source_text` 与消息上下文中正文的重复体积。第一阶段保持所需语义；若体积构成瓶颈，再定义严格的轻量投影及按需来源读取，不直接删字段、截断历史或伪造来源。
10. 现有阅读、任务等独立 GET 若仍服务轮询、手动刷新或其他页面，应保留其正常用途；删除的是重复首屏调用，不是仍在使用的接口。不要为旧数据增加兼容通道。

预期初始链路：

```text
实际进入作业
  → 一次工作区响应：身份/归属、当前稿或暂存稿、辅导摘要、阅读/只读状态
  → 如有需要：一批聊天历史与任务状态请求
  → 完整工作区可用

后台独立执行：通知已读 → 角标刷新；侧栏更新；辅助摘要与按需材料
```

后台请求也要去重并限制并发，避免把大量辅助请求同时推入浏览器连接队列，挤占关键请求。

### 阶段 C：首页短时复用与刷新治理

本阶段只处理首页列表和展示状态，**不新增正文写回缓存、不持久缓存写权限、不替代现有稿件备份机制**。

推荐实现一个小范围、可测试的内存数据层，不为这一个页面引入整套大型缓存框架。

- 缓存键至少包含站点／当前身份代次、用户 ID、教学角色、班级范围与筛选参数。不得只按 URL 共享。
- 默认不写入 `localStorage`／IndexedDB，也不让 Service Worker 缓存带身份的工作区、通知或权限响应。
- 初始建议短时窗口 15 秒，可通过测试调整。TTL 是资源限制，不是权限撤销保证。
- 同一键共享在途请求；已离开页面的消费者不得更新当前页面状态。新账号必须开启新代次并清除旧账号数据。
- 有可用快照时可以保留筛选、分组和滚动位置；数据刷新不重置用户当前分段，不将编辑器重新挂载。
- 新发布、修改、隐藏／恢复、批改、退回、入班／调班、自己提交／撤回，以及重新登录、角色变化和 Socket 重连，都要使相关数据失效或重新校验。
- 不只比较未读数量：数量不变也可能有新的业务事件。也不要让每次角标赋值无条件刷新全首页。
- 请求期间收到新通知时保留“待再次刷新”标志，在在途请求结束后合并执行，避免当前 `homeLoading` 直接跳过事件而漏更新。
- 隐藏、撤权和账号切换事件到达后立即移除相关显示。若无法可靠满足当前隐藏可见性规则，默认只缓存布局和筛选条件，继续等待服务器列表；不能为了达到 150 ms 目标展示未经校验的已失效作业。
- 网络失败时区分缓存预览与最新结果；不得把旧列表标成刚更新。任何 401／403 均清除不再有权使用的数据并按现有登录／权限流程处理。

本阶段可以在阶段 B 后实施；不以缓存“遮住”尚未解决的关键请求串行等待。

### 阶段 D：后台查询与大内容优化，按证据实施

#### D1. 查询

当前 `get_writing_home` 会遍历会话和作业，并逐项装配记录。代码上存在重复查询／逐项查询的检查空间，但本轮线上没有 SQL 时间和查询次数证据，不先宣称数据库是主要瓶颈。

在隔离环境记录 SQL 次数与时间、响应大小及序列化时间，再决定是否批量获取、只选必要字段或增加索引。业务计算放入服务层。不得为短期性能增加一个难以失效的全局权限缓存。

若修改 SQL、约束、列类型或迁移，除 SQLite 外须按仓库规范跑专用 PostgreSQL 测试；不得连接生产数据库进行压力测试、清理或迁移试验。

#### D2. 渲染与资源

只有当浏览器测量显示网络已结束但内容仍迟迟不可用时，才进入此项：

- 区分编辑器结构解析、Markdown、图表／代码高亮、图片解码和长任务耗时。
- 对未打开的导入、Word 下载、预览和其他重组件按需加载；测量生产构建的资源包，不拿 Vite 数千模块的冷编译请求当线上包体。
- 长聊天可优化渲染范围，历史仍可访问，分支、搜索、来源、跳转与滚动定位保持正确；不直接删减已保存消息。
- 图片／原件二进制按需获取，稿件所需结构和资源引用先恢复；不要显示空正文冒充完整图文稿。
- 角色无关的管理界面代码如确实进入学生首屏，再调整加载边界；不顺手重构全站导航。

## 7. 页面状态与失败处理

| 情况                     | 应有行为                                                     | 禁止行为                            |
| ------------------------ | ------------------------------------------------------------ | ----------------------------------- |
| 初次恢复工作区           | 中性加载提示，必要状态齐全后展示正确稿件                     | 把查询历史显示成 AI 正在阅读        |
| 已有成功或失败初读       | 恢复原对话与稿件，按真实状态可编辑／只读                     | 重新发起初读、先开空聊天再跳转      |
| AI 确在生成              | 真实等待态、恢复任务与阅读进度                               | 为了加速先解锁编辑或提交            |
| 阅读状态读取失败         | 显示可理解错误，不推断“没有初读”；遵守现有允许／禁止提交规则 | 把失败响应转换为空列表并自动生成    |
| 辅助请求失败             | 相应局部状态可重试，稿件和输入保持                           | 整页回到加载、清空编辑器            |
| 工作区权限或身份失效     | 终止加载并按现有规则提示／登录                               | 从缓存开放写入、展示另一账号数据    |
| A 作业切到 B，A 响应晚到 | 忽略 A 对 B 的更新；必要时取消旧读取                         | 覆盖 B 的稿件、模型、通知或侧栏选择 |
| 服务器返回时学生已在编辑 | 不用旧响应覆盖新输入；保存仍遵守 revision                    | 定时刷新整个工作区覆盖编辑器        |
| 刷新后发现本地备份       | 保留现有核对、下载和显式恢复步骤                             | 静默覆盖服务器稿件                  |

所有进入、刷新与退出路径均检查计时器、订阅、滚动回调和迟到 Promise 的生命周期。页面移除时不得残留错误、无限轮询或新写请求。

## 8. 可复现测量规范

### 8.1 指标定义

- `T_click`：页面实际收到目标控件点击事件的时刻。
- `T_preview`：有效缓存内容可见；可选，不能代替下列完成指标。
- `T_fresh`：本次服务器状态核对完成。
- `T_workspace_ready`：当前稿／暂存稿、适用锁定状态、辅导配置，以及原本存在的对话均恢复；编辑或只读行为与服务器事实一致。
- `T_home_ready`：本次列表数据已渲染；展开已有分组的手动操作单独计时。

若进入时 AI 已经在生成，完成判据是正确恢复已有内容与真实等待状态，不需要等该次 AI 回复生成结束。模型生成耗时与页面导航耗时分别记录。

页面秒表用浏览器时钟，导航跨文档时可在临时 sessionStorage 中传递测量起点；检测 `performance.timeOrigin` 和主文档请求确认是否整页刷新。测量结束清除临时监听和测量键，不清除真实聊天输入、备份和用户存储。

不使用 `page.click()` 工具调用总耗时、固定 sleep、转圈消失或单次 API 返回时间冒充页面完成时间。对空稿检查编辑器确已恢复并具备正确可编辑性；对聊天检查原消息已显示。网络图中并行时间不能重复相加。

- 没有修改 SQL 语义、索引、约束或迁移，没有改画像或新增内容缓存；只抽取既有摘要／试读查询并在既有工作区中调用。不扩大成全站渲染或查询重构。

### 12.2 测量方法

### 12.4 后端与完整性验收

真实后端使用 Alembic 创建的临时 SQLite 库和模拟模型。`backend_profile.py` 对每种规模的 workspace 与 chat GET 各测 20 次；完整数据见 [backend-profile.json](assets/workspace-performance-20261112/backend-profile.json)。

| 规模 | workspace P50 / P95 | chat P50 / P95 | workspace / chat SQL 次数 |
| --- | ---: | ---: | ---: |
| 2000 字 / 10 消息 | 12.0 / 13.8 ms | 6.6 / 8.2 ms | 16 / 4 |
| 2 万字 / 50 消息 | 36.5 / 42.3 ms | 20.4 / 24.1 ms | 16 / 4 |
| 10 万字 / 200 消息 | 293.7 / 334.0 ms | 283.0 / 330.6 ms | 16 / 4 |

这是 TestClient 单请求诊断，包含处理／序列化及测试框架开销，不是网络 RTT。查询次数稳定；压力样例真实后端聊天 JSON 达 23,466,049 字节，说明后续大规模优化应优先研究不可变上下文的轻量读取契约，而不能仅通过加索引解决。本轮保留全部来源、消息与冻结证据，不截断或去掉字段。
