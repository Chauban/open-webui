## 用户要解决的问题

“我的作业”和“继续写作”每次进入都要等，几秒前访问过也不变快；此前还出现过空对话和假“AI 正在阅读”中间画面。目标是加快真实稿件与原对话的恢复，并保持保存、权限、初读、提交和只读规则。

2026-11-12 同一浏览器线上三轮基线：南科大首页约 0.44 秒、空稿工作区约 2.00 秒；哈工深首页约 0.46 秒、空稿只读工作区约 1.68 秒。两者均未整页刷新，重复进入无明显改善。每次接口往返约 0.4 秒，workspace、通知已读、通知摘要、辅导配置依次等待；南科大还在组件挂载后读取 pending-draft。

这些样本没有历史对话，不代表长稿续写。原始逐次数字、计时方法、限制与验收目标在方案里。先补充隔离环境下有稿有对话的基线。

## 执行顺序

1. 核对并补齐已有前端优化，确认慢通知／慢标签不再挡住正文，处理重复请求和迟到响应。
2. 按方案减少必要网络轮次，优先扩展现有工作区响应，把适用的辅导摘要、阅读／锁定状态、未确认初稿暂存状态一起恢复。复用后端服务，不能在聚合接口内请求自己的 HTTP 路由，也不能并发使用同一个数据库 Session。
3. 调整 DraftBaselineStep 和 Chat 的初始数据消费，避免同一数据重复获取和重挂载覆盖输入；恢复历史不启动模型。
4. 实现有边界的首页复用、在途请求去重和事件刷新。按账号／身份／班级隔离，处理隐藏、撤权、重新登录、Socket 重连及迟到响应。不能保证正确失效时，不启用未经校验的作业内容缓存。
5. 只有查询、响应体或渲染测量支持时，才进一步改查询、索引、重组件和长列表；不要扩大成无证据的全站重构。
6. 新增有实际意义的回归测试，使用生产构建测量，并按方案的状态和数据规模矩阵验收。完成后同步 Userflow、当前任务清单与方案实施状态。

方案给出了推荐边界，你可以基于新证据调整实现细节，但要说明原因并更新原方案；不要另建重复文档。先处理核心数据链路，不先用骨架屏或缓存预览冒充可用时间。

## 不可破坏的规则

- 服务器继续执行身份、归属、隐藏、定稿和写入权限校验。
- 当前规则下超过截止仍可写作和提交；已批改仍只读。
- AI 真正在生成时继续锁定；已完成／失败初读只恢复，不自动重发或创建新对话。
- 稿件、来源、历史消息、冻结提交、未发送输入及本地备份不能丢失或被旧响应覆盖。
- 不自动恢复本地稿覆盖服务器，不跨账号共享缓存。
- 当前 workspace GET 可能创建资源／恢复侧栏可见性，因此不用于悬停或批量预取；不要因“加速访问”自动创建作业资源。
- 不为旧脏数据增加兼容、回填或自动修复，不在普通读取中重算画像。

## 测试与完成标准

从 `open-webui/` 运行仓库规范要求的前端全量测试、增量类型检查、生产构建和 `git diff --check`；改后端就运行相关 pytest，使用 `backend/.venv`；改 SQL／迁移等还须专用 PostgreSQL 验证。不要使用生产数据库做测试。

性能计时从浏览器实际点击开始，到真实列表／稿件与已有对话恢复结束。区分缓存预览、新鲜状态校验、整页冷启动与应用内往返。至少覆盖空稿、有稿有对话、长稿、生成中、失败、只读、快速切换、保存失败和未同步备份。测试数据与模型调用使用隔离环境和模拟模型，不在真实学生稿件里造数据。

第一阶段目标：接近本次约 400 ms 接口往返的网络条件下，普通工作区 P50 ≤ 1 秒、P95 ≤ 1.5 秒；具体样本量和长稿目标见方案。不能达标时继续定位可处理瓶颈，并如实交代限制，不虚报成功。
