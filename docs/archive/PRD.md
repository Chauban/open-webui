# RightWrite 产品需求文档（PRD）

## 1. 文档信息
- 产品名称：RightWrite
- 文档类型：产品需求文档（PRD）
- 文档版本：V1.6
- 更新时间：2026-09-07
- 适用对象：产品、设计、前端、后端、测试、项目管理
- **适用学段：大学（本科）写作类课程**——如「写作与交流」「学术写作」「学术论证写作」。不面向中小学，文档、界面文案与演示数据一律不使用「中学生」「八年级」「班主任」等中学语境，也不使用「议论文」「记叙文」「说明文」这类中学文体分类；对应说法是**学术论证写作 / 课程论文 / 文献评析 / 文献综述 / 研究计划 / 个人陈述**。
- 文档范围：基于当前 `right_chat/open-webui` 工作区的现状与后续演进方向

## 2. 产品概述
RightWrite 是一个基于 Open WebUI 深度改造的**大学写作课教学产品**，核心目标不是通用聊天，而是围绕“教师布置任务、学生在 AI 辅助下写作、教师回看过程并完成评阅”的完整教学闭环。

**使用者是大学本科生与其任课教师**，典型课程是「写作与交流」这类通识写作课，典型任务是学术论证写作、课程论文、文献评析与个人陈述。这一点决定了产品的很多取舍：评分维度按学术论证的要素设计（论点的可辩驳性、证据与来源、反方处理），而不是中学作文的「立意/结构/语言」；AI 的角色是学术写作助教而非作文辅导老师。

当前产品已经具备以下基础：
- 教师端课堂管理、作业管理、概览页、评阅队列
- 学生端作业写作工作台
- 写作过程追踪，包括版本、Prompt 时间线、来源高亮、反思信息
- 教师端提交详情与结构化评分/评语保存能力
- 成长画像的证据固化与版本化指标计算
- 学生侧的数据采集告知，与面向教研的假名化数据导出

因此，RightWrite 的产品定位应定义为：

`面向教学写作场景的 AI 辅助写作与评阅平台`

它与原始 Open WebUI 的区别在于：
- 原产品以多模型聊天与知识增强为核心
- RightWrite 以教学任务组织、写作过程留痕、教师审阅反馈为核心

## 3. 产品愿景
构建一个让教师能够放心使用 AI 写作工具进入真实课堂的教学平台。

平台需要同时满足三件事：
- 学生可以在 AI 支持下完成写作，但过程可记录、可解释、可回看
- 教师可以按课堂和作业组织教学活动，而不是在聊天记录里寻找证据
- 教师能够基于过程数据而非仅最终结果，完成评阅、反馈和教学复盘

## 4. 目标用户与角色
## 4.1 教师
核心诉求：
- 创建和管理课堂
- 向指定课堂发布写作任务
- 查看学生是否提交、何时提交、如何使用 AI
- 审阅学生终稿与写作过程
- 给出评分、评语和退回修改意见

## 4.2 学生
核心诉求：
- 通过课堂加入课程
- 进入指定作业的专属写作空间
- 在 AI 对话辅助下进行写作
- 保存草稿、提交终稿、填写 AI 使用反思
- 接收教师反馈并继续修改

## 4.3 管理员
核心诉求：
- 管理平台用户和权限
- 审批与调整教师/学生教学身份
- 维护三档 AI 辅导风格的措辞
- 导出教研数据用于前后测与统计分析
- 维护平台基础模型与系统配置

## 5. 核心问题定义
传统 AI 聊天产品直接用于教学时，通常存在以下问题：
- 教学对象缺失：无法按课堂、学生、作业组织任务
- 写作过程缺失：只能看到结果，看不到修改和 AI 使用轨迹
- 教师工作流断裂：能查看内容，但难以形成待办、批改、反馈闭环
- 结果可信度不足：教师无法判断学生内容中哪些来自自主写作，哪些来自 AI 帮助
- 教学复盘不足：无法按班级或作业进行整体分析

RightWrite 的产品价值就在于解决这些问题。

## 6. 产品目标
## 6.1 业务目标
- 将通用 AI 对话工具转化为可落地的教学写作平台
- 建立教师端“课堂-作业-提交-评阅”的标准化流程
- 建立学生端“写作-保存-提交-反思”的标准化流程
- 为后续教学数据分析、风险识别和班级管理奠定结构基础

## 6.2 用户目标
- 教师进入系统后，能快速知道当前要处理什么
- 学生进入系统后，能快速找到自己要写什么
- 教师评阅时，不只看到终稿，还能看到写作来源和过程证据

## 6.3 产品成功标准
- 教师可以独立完成从建班到评阅的完整流程
- 学生可以独立完成从加入课堂到提交作业的完整流程
- 教师在一个页面内完成主要审阅动作，而不是跨多个聊天页面跳转
- 平台可区分 typed / AI inserted / AI pasted 等来源数据

## 7. 产品定位与范围
## 7.1 当前产品范围
当前版本聚焦**大学写作类课程**教学场景，优先支持：
- 单教师管理多个课堂
- 单课堂内学生加入
- 教师发布写作作业
- 学生在专属写作空间完成作业
- 系统记录写作过程与 AI 使用信息
- 教师对提交内容进行评阅和反馈

## 7.2 暂不作为当前核心范围
- 家长端
- 复杂排课系统
- 跨学科教学资源库
- LMS 全量替代
- 自动化教务结算或学籍管理

## 8. 关键使用场景
## 8.1 教师布置写作任务
1. 教师创建课堂
2. 分享邀请码给学生
3. 在课堂下创建作业
4. 复制学生写作链接或引导学生进入作业

## 8.2 学生完成 AI 辅助写作
1. 学生加入课堂
2. 打开作业写作页面
3. 在右侧编辑器和左侧对话区协同写作
4. 系统自动保存草稿并记录版本
5. 学生提交终稿并填写 AI 使用反思

## 8.3 教师回看与评阅
1. 教师在 Overview 或 Review 队列看到待评项目
2. 打开某个 submission 的详情页
3. 查看终稿、来源高亮、统计、reflection、prompt timeline、version history
4. 填写分数、总评、rubric、退回意见
5. 保存评阅或退回修改

## 8.4 教学复盘
1. 教师进入 assignment dashboard
2. 对比不同学生的 typed / AI inserted / AI pasted / prompts / reflection 覆盖
3. 查看全班在哪些评分维度上没答住，必要时触发论证类型归纳
4. 形成班级层面的教学判断，并把某个维度设为下次作业的质疑焦点

## 8.5 教研数据导出
1. 管理员进入 Education 面板
2. 按班级与提交时间范围导出数据集
3. 用假名化、带算法版本的数据做前后测与统计分析

## 10. 当前已实现能力
以下内容基于当前代码与测试可确认的能力，而不是规划态功能。

### 10.1 账号与教学身份
- 教学身份由两个系统权限组承载：`education-teacher` / `education-student`，不写入用户 info
- `user.role` 保持上游语义（平台权限与 `pending` 审批闸门）；平台管理员一律视为 `admin`，可同时兼任教师
- 权限组同时决定"这个人在课程里是谁"和"他能用到什么"（模型、工具、功能），无需二次同步
- 教学身份只有一个写入口：变更身份会级联清理不再匹配的班级成员记录
- 仍拥有班级的教师禁止降级或撤销身份，须先转交班级
- 教师相关接口具备访问权限校验

### 10.2 课堂管理
- 教师创建课堂
- 系统自动生成邀请码
- 学生通过邀请码加入课堂；**一个学生只能在一个课堂**（数据库唯一约束兜底，已入班的学生页面上不再出现加入入口）
- 教师查看课堂列表
- 教师查看课堂成员并进行增删、批量导入、批量移除，以及在本人课堂之间转移学生
- 换班：原班教师移出后学生凭新码加入；跨教师调班由管理员在编辑用户弹窗完成。换班后提交记录留在原课堂，原教师可继续查看与批改；成长画像跟着学生走，包含换班前交过的作业
- 教师可重新生成邀请码
- 教师查看班级进度、未提交名单并导出进度

### 10.3 作业管理
- 教师向一个或多个课堂创建作业
- 作业绑定课堂
- 教师查看全局作业列表
- 教师查看课堂下作业列表
- 教师编辑作业标题、描述、所属课堂、状态、截止时间
- 教师设置评分总分与评分维度（维度配分之和必须等于总分）
- 教师按作业选择 AI 辅导风格档位（严格提问 / 平衡 / 放手），档位措辞由管理员维护
- 教师归档作业
- 教师复制学生写作链接
- 教师查看未提交学生并发送催交通知
- 教师给单个学生设置个人截止时间（延期），不影响全班
- 教师从已有作业复制创建新作业

### 10.4 学生写作工作台
- 学生进入 assignment workspace
- 系统为作业创建专属 folder/project
- 左侧聊天、右侧写作编辑区协同使用
- 自动保存草稿
- 自动创建写作版本
- AI 插入内容可直接插入正文
- AI 复制内容可携带来源标记
- 作业要求与评分维度在写作区展示，并注入对话上下文
- 所选辅导风格作为辅导约束追加到作业对话上下文
- 学生可看到本次写作构成（自己敲的 / AI 插入 / AI 粘贴 / 外部粘贴 / 来源未记录占比）与已回答澄清追问数，只呈现不评判；作业写作仅在定稿（已批改或已截止）后显示，写作过程中不显示，防止学生盯着比例刷数
- 支持独立于作业的个人写作空间
- 写作区展示数据采集告知：记录了哪些行为、作业写作教师可见、个人写作空间教师不可见
- 学生可查看历史轮次、教师反馈和成长画像

### 10.5 过程追踪与留痕
- 保存 writing session
- 保存 writing version
- 保存 provenance segment
- 记录 `user_typed` / `ai_inserted` / `ai_pasted` 等来源
- 记录 active chat
- 记录 micro reflection
- 记录 prompt timeline
- 记录 editor operation，客户端毫秒发生时间、客户端顺序与服务端接收时间分开保存
- 从 assistant 消息中派生 AI 澄清追问问答对（上游 `ask_user` 工具），纯派生、不建表、不依赖前端上报
- 学生在加入班级页与写作区两处被告知过程被记录；告知只说采集范围与可见边界，不含任何指标名与阈值（见 12.11）

### 10.6 提交与评阅
- 学生提交终稿
- 教师查看 submission 列表
- 教师查看 submission 详情
- 页面支持来源高亮阅读
- 教师可填写 review status、score、结构化 rubric 维度得分、overall comment、returned comment
- 每次批改追加一条不可变 review event，评阅历史只追加不覆盖
- 教师批改时给反思质量 1—5 分，是成长画像该维度的唯一来源，标记为已批改时必填
- 提交详情展示 AI 澄清追问过程证据（提问 / 回答 / 自由作答 / 跳过计数，只展示不计入画像指标）
- 学生端按评分维度名称与该维度满分查看得分，总分带满分分母，历史轮次同样如此
- 支持 `pending` / `reviewed` / `returned`
- 退回后开放下一轮提交，并保留各轮终稿、评阅与差异
- 已批改即定稿，除非教师明确退回，否则禁止继续提交
- 提交、批改、退回和催交会生成站内通知

### 10.7 提交前读者试读
- 教师按作业开启，设置回合数（2 或 3）与质疑焦点（从本作业评分维度勾 1~2 个）
- 学生点提交后先进入试读：契约声明 → 有限回合问答 → 收尾清单 → 回去修改或继续提交 → 反思 → 提交
- 回合数由服务端代码控制，跳答、重复答、超轮一律拒绝
- 学生可跳过，跳过状态记录并对教师可见
- 收尾清单回流写作面板，勾选状态持久化
- 教师在提交详情看到逐轮问答、是否跳过，以及收尾之后正文有没有实质修改
- 本轮生效的质疑措辞与状态在提交时冻进 `stats_json`，管理员改词不影响已交轮次
- 质疑事实进入成长画像的「面对质疑」维
- 教师退回时可勾选「让读者下一轮就着这条意见追问」，退回意见成为下一轮质疑的焦点

### 10.8 教学概览与分析
- 教师概览页展示课堂数、作业数、待评数、未提交数
- 展示 recent assignments、recent submissions、pending review queue
- assignment dashboard 提供来源统计、风险摘要与反思覆盖数据
- 班级进度页聚合作业和学生维度状态
- 成长画像展示写作投入、修订深度、AI 协作、反思质量、趋势与轮次进步
- 成长画像拆分为不可变证据快照与可重算指标投影，算法按版本发布
- 教师可在班级学生页记录私有观察笔记（含修订历史）
- 学生可维护自己的成长目标
- 指数公式与阈值只在教师端画像返回，学生端响应不含该字段（见 12.11）

### 10.9 班级质疑分析
- 看板按评分维度给出全班被质疑人数、没答住人数与被质疑处一字未动人数，纯内存聚合、不调模型
- 可一键把某个维度设为下次作业的质疑焦点，复用作业复制流程连 rubric 一起带过去
- 教师手动触发时才调模型，把没答住的点归纳成 3~5 类论证类型，按输入哈希缓存
- 完成试读少于 5 人直接拒绝出结论且一次模型都不调；送模型的载荷不含任何身份字段

### 10.10 教研数据导出（管理员）
- 按班级与提交时间范围导出 zip：三张 CSV 加一份口径 README
- 学生身份由服务端密钥 HMAC 假名替代，稳定不可逆，导出不含姓名与邮箱
- 每行携带指标算法版本与代码校验和，跨批次数据的可比性可被检出
- 反思原文默认不导出，需显式开启

## 11. 核心业务流程
## 11.1 教师流程
`创建课堂 -> 管理学生 -> 创建作业 -> 监控提交 -> 打开评阅 -> 保存反馈 -> 进入复盘`

## 11.2 学生流程
`加入课堂 -> 打开作业 -> AI 辅助写作 -> 自动保存 -> 提交终稿+反思 -> 接收反馈 -> 被退回后进入下一轮`

## 11.3 数据流程
`classroom -> assignment -> writing_session -> versions/provenance/operations -> submission rounds -> submission_review`

提交与批改同时向画像侧追加不可变记录，画像只读派生数据，不回读原始版本、编辑操作、来源映射或聊天记录：

`submission -> profile_evidence_snapshot + submission_review_event -> profile_metric_projection -> student_profile_aggregate_projection`

这个链路是 RightWrite 区别于通用聊天产品的关键资产。

## 12. 核心功能需求
## 12.1 教师端概览（Overview）
目标：回答“现在最该处理什么”。

需求：
- 展示关键指标：课堂数、作业数、待评数、未提交数
- 展示待评队列
- 展示最近提交
- 展示最近作业
- 展示课堂概览
- 从概览页一跳进入 review / assignments / classrooms

## 12.2 课堂管理（Classrooms）
目标：回答“我在管理哪些班级”。

需求：
- 创建课堂
- 查看邀请码
- 查看学生人数与作业数量
- 进入课堂详情
- 进入学生页和作业页
- 批量导入、移除或转移学生
- 查看班级进度、未提交名单并导出
- 对单个学生延长截止时间并可随时撤销

## 12.3 作业管理（Assignments）
目标：回答“我布置了哪些任务，哪些任务需要处理”。

需求：
- 按课堂、状态、关键词筛选
- 查看学生数、提交数、最新活动
- 打开作业详情
- 复制学生链接
- 进入 submissions 与 dashboard

## 12.4 作业详情（Assignment Detail）
目标：回答“这个作业当前是什么状态，接下来去哪处理”。

需求：
- 展示学生数、提交数、状态、截止时间
- 编辑标题、描述、所属课堂、状态、截止时间
- 设置评分总分与评分维度，维度配分实时校验
- 选择 AI 辅导风格档位
- 复制为新作业，沿用标题、要求、评分维度与辅导档位
- 支持归档
- 支持跳转到提交列表、分析页、所属课堂

## 12.9 AI 教学角色与提交前质疑环节
目标：回答“AI 在这个产品里扮演几个角色，学生分得清吗，教师控得住吗”。

### 12.9.1 背景问题
当前 AI 只有一个角色：写作过程中的辅导助手。`coaching_style` 三档（严格提问 / 平衡 / 放手）不是三个角色，而是同一个助手的三种克制程度，控制的都是“AI 帮多少”。学生始终是索取方，AI 始终是给予方。由此带来两个结构性缺口：

- 平台的过程数据以“用了多少 AI”为主（来源占比、prompt 数），属于监控指标，回答的是“有没有作弊”，而不是“学到了什么”
- 缺少一种 AI 输出无法进入正文的使用方式，防代写只能依赖留痕与事后解释

### 12.9.2 角色划分
平台只设两个 AI 教学角色，不再增加。

辅导助手（Tutor）
- 契约：学生问、AI 答，AI 提供帮助
- 位置：写作区左侧聊天，常驻
- 输出可进入正文：可以（Insert 插入或带来源标记的复制）
- 约束来源：作业的 `coaching_style` 三档

质疑读者（Challenger）
- 契约：AI 问、学生答，AI 不提供帮助
- 位置：提交前的独立回合流程，不进入聊天框
- 输出可进入正文：不可以，其输出是质疑而非可用文本
- 约束来源：作业的质疑配置（开关 / 回合数 / 焦点维度）

两个角色的对话契约相反，因此**不做模式切换，做物理分离**。质疑读者不进入聊天框；学生若想让辅导助手代答质疑，必须切回左侧提问，该行为会出现在 prompt timeline 中，教师可见。平台不做拦截，只做暴露。

`coaching_style` 的语义收窄为“只约束辅导助手”，不得引入质疑口吻；质疑读者也不承担辅导职能。角色单一是学生建立稳定预期的前提，混合会让两个角色同时失效。

### 12.9.3 流程与时机
质疑环节挂在提交前，位于现有反思弹窗之前：

`点击提交作业 -> 质疑回合（2~3 轮） -> 收尾清单 -> 回去修改 或 继续提交 -> 反思 -> 提交`

需求：
- 不设常驻入口。正文为空时进入质疑没有教学意义
- 每一轮由服务端发起，回合数由服务端控制，不依赖模型自觉遵守提示词
- 质疑只针对论证，不针对作者本人，不评论文采
- 最后一轮结束后必须收敛，产出“哪些回应站得住 / 哪些还不成立”的清单
- 学生可跳过，跳过状态记录并对教师可见；不设强制拦截

### 12.9.4 学生侧需求
- 入口文案与 AI 首句必须先声明契约（“我是一个不同意你的读者，我不会帮你改，只说哪里说服不了我”），否则学生会持续向其求助并判定 AI 无用
- 界面为卡片式单轮推进，不是聊天流：一条质疑、一个回应输入框、一个提交动作
- 收尾清单回流到写作面板，成为可勾选的修改待办
- 收尾必须提供“回去修改”出口，使质疑能够真正作用于正文
- 入口与标题不使用“对抗”“挑战”“找茬”等措辞，避免学生进入防御姿态

### 12.9.5 教师侧需求
教师控制“考不考、几轮、对着什么”，不维护措辞；措辞由管理员维护，与三档辅导风格同一机制。作业上只设三个控件：

- 是否启用提交前质疑
- 回合数（2 或 3，不提供无限）
- 质疑焦点：从本作业 `rubric_schema.criteria` 中勾选 1~2 个维度

焦点直接复用评分维度，教师无需学习新概念，且学生被追问的点即最终被扣分的点，质疑方向与评分标准天然对齐。未配置评分维度的作业不允许启用质疑。

### 12.9.6 教师回报
不新增页面。在 submission detail 中增加“质疑回合”区块：

- 每轮的质疑点与学生回应
- 学生是否跳过
- 回应之后被质疑的那处正文是否发生变化（由发起质疑时冻结的 `source_version` 快照与最终提交正文比对得出，口径见 12.9.8）

该区块提供的是学生思考过程的直接证据，与现有来源占比统计互补：来源统计回答“他用了多少 AI”，质疑回合回答“他被问住之后做了什么”。

### 12.9.7 留痕信任层级
按第 15 条非功能需求，本环节的数据必须分层解释，不得在教师界面混同：

- 质疑文本、回合数、收尾清单：服务端生成，权威
- 学生回应文本：学生自己输入，可信度等同 typed 正文
- 回应后是否修改正文：两份服务端快照直接比对得出，同样权威，不依赖客户端上报，也不受客户端时钟影响

因此本环节的三类数据全部落在服务端权威层，不适用来源占比那套「客户端记录、可能不完整或被绕过」的口径。教师界面不得把这两层混同呈现——给质疑回合挂来源留痕的免责说明，会把权威数据错误地降级。

### 12.9.8 修订判定：从「改了多少」到「改在哪」
以「全文字符改动量是否超过最小阈值」判断学生被质疑后是否修改，方向是反的，必须替换：

- 被质疑后最理想的修改往往是最小的修改：删掉一个站不住的例子，或把「所有人都认为」限缩为「我采访的 12 个同学里有 9 个认为」。这类改动字符数极小，会被判为未修改
- 反之，在结尾补一句与质疑无关的套话即可越过阈值，被判为已修改
- 全文比对不看位置：质疑打的是「论据支撑」，学生改的是结尾抒情段，同样判为已修改
- 收尾清单的勾选由学生自行操作，三条全勾而一字未改在数据上完全成立

判定口径因此改为：**被质疑的那处正文有没有变**。

- 每一轮质疑必须引用它所质疑的原文片段，该片段作为结构化字段随回合落库（见 13.21 `quoted_span`）
- 修订判定改为：被引用的片段在最终提交正文中是否发生变化。仍是两份服务端快照比对，不依赖客户端，符合 12.9.7 的信任层级
- 位置正确的小改动即为有效修改，字符数阈值相应下调或取消
- **不引入「AI 判断学生是否真的回应了质疑」**（2026-09-09 定案否决，理由见 16.4）：片段级判定 + 教师并排呈现即为最终形态。片段级判定挡不住「在被质疑那句里改两个无关的字」，这个缺口由教师看三栏证据承担，不由系统补
- 教师侧三栏并排呈现：被质疑的原文片段 / 该片段在最终稿中的样子 / 学生当时的回应。结论由教师下，系统只负责把三样东西摆在一起

强制引用原文另有一项附带收益：质疑无法再停留在「你的论据不够充分」这类空泛表述，必须落到具体句子。

### 12.9.9 学生侧质疑记录的可回看性
质疑往来目前只在对话框内可见。学生点击「回去修改」关闭对话框后，写作面板只保留收尾清单的未解决条目，且没有任何入口可以重新打开质疑记录——再次点击提交时本轮质疑已结束，流程直接进入反思弹窗。

同时教师端 submission detail 保有全部往来。这一不对称的方向是错的：真正需要这份记录去修改文章的是学生。

- 写作面板的收尾清单可展开查看本轮完整往来（每轮质疑与自己的回应），默认折叠
- 数据不额外请求，复用写作面板已持有的质疑详情
- 引入 `quoted_span` 后，清单每条可点击定位到正文对应位置
- **不在正文中做常驻高亮标记**。写作区被划满标记会让学生进入防御姿态，与 12.9.4「不使用对抗性措辞」是同一条原则。点击才定位，不点不显

### 12.9.10 回避信号的完整记录
跳过质疑是本环节最有教学意义的信号之一——系统性回避质疑的学生，正是最需要被教师看到的那批。但目前只有「已开始后跳过」会落库；在契约声明页尚未点击开始就跳过的学生不产生任何记录，教师端连「已跳过」都看不到，该次提交在质疑维度上完全空白。最该被捕捉的那种回避，恰好是唯一没有留痕的。

- 启用了质疑的作业，学生在契约页跳过同样落一条 `status = skipped` 的记录
- 教师端与画像不区分「已跳过」与「未开始」：对教师而言两者是同一件事
- 仍不设强制拦截。产品只负责让回避可见，不负责阻止回避

### 12.9.11 自适应焦点（待观察，形态未定）
焦点目前在教师勾选的维度间机械轮转。真实读者不这样读：学生答得住就换角度，答不住就在原地追问。

- 下一轮焦点由上一轮回应决定，而非按轮次固定轮转
- 需要每轮输出附带「上一轮是否已被回应」的结构化字段，供服务端选择焦点
- 教师配置不变，仍只勾选 1~2 个维度，自适应发生在这些维度内部

**这一节不是待排期的需求，是待观察的假设。** 2026-09-09 讨论后明确：不得因为 16.4 否决了 AI 判定就把该需求顺手挪到这里实现。

选焦点必须先判「上一轮答住了没有」，这与 16.4 否决掉的判定是同一个能力，区别只在消费者——前者是路由信号（误判的后果是多问一轮，学生下一轮当场可纠正），后者是落库结论（误判的后果是学生看不见、无法答辩的永久记录）。区别真实，但比它看上去的小，且**严重性方向相反**：判定的误判只落在有争议的少数人身上，追问偏置落在每个学生的每一次。模型对「这个回答够了吗」有天然偏置——它几乎总能找出不够的地方，这是任务形式自带的，不是提示词能调好的。

由此产生的风险是**质疑读者退化成杠精**：同一句被追第二遍第三遍；学生已经承认了局限还在被问；语气的攻击性在同一处累积——第一遍说「我没看懂」很自然，第二遍再说同一句很难不滑向「你还是没说清楚」，而 12.9.4 的「不使用对抗性措辞」恰恰在同处重复时最难守住。

**因此本节在有真实课堂观察之前不进入实现。** 需要先回答的是观察题而非推理题：机械轮转到底够不够用、学生在第 2 轮是否已经不愿意答、收尾清单能否把气氛拉回来、质疑是否真的落在勾选的维度上（见 12.10.1 的标签一致性问题）。

真要做时必须带三条护栏，缺一条即不做：

- **判据下沉**：不判「答得好不好」，只判「答了没答」（回应为空、或只有表态没有内容）。这个判据可靠得多，且误判时学生不觉得冤——他确实只写了一行
- **追问硬上限 1 次**：同一处最多问两轮。杠精的定义是不肯罢休；结构上封死「没完没了」，误判的代价上限就锁死在「多问了一轮」
- **收尾清单的「站得住」部分只许加强不许缩水**：被追问过的学生尤其需要看到自己哪里是对的。这是防杠精的结构性解药，杠精不会承认对方哪里对

### 12.9.12 教师退回意见驱动的追问
退回重交的闭环目前止于教师写下退回意见：学生看不看、改不改全凭自觉，教师没有任何抓手。而质疑引擎恰好具备「盯住一个点反复追问」的能力，只是它的焦点目前只能来自 rubric 维度。

- 教师退回作业时可勾选「让质疑读者就这条意见追问」
- 焦点维度仍按 rubric 轮转，教师的退回意见叠在上面作为该轮的首要指向。**不替换维度**：
  替换会让每一轮的 `focus_key` 失去意义，班级层面的维度聚合（12.10.1）和该列的非空
  约束都会跟着塌
- 意见原文在发起质疑时冻进本轮记录，与冻结提示词同一道理：评语可以事后被改，已经
  开始的这一轮不能跟着变
- 未启用质疑的作业不显示也不接受该勾选——不在这里替教师悄悄打开质疑环节；没退回或
  没写意见同样拒绝，没有内容可追问时不该硬造一轮
- 学生下一轮提交前的质疑围绕这条意见展开，回合数沿用作业配置
- 复用现有回合引擎与全部界面，不新增学生侧概念

这是产品中第一处 AI 直接执行教师教学意图、而非执行配置预设的交互。

## 12.10 班级质疑分析（教研回报）
目标：回答「AI 除了服务学生，能不能服务教师的教学决策」。

平台目前对教师的全部回报都是个体的（提交详情、成长画像），班级层面的聚合只有来源占比与改写程度分布——都是监控指标，回答「有没有作弊」。质疑环节产生了第一批可聚合的**学习指标**：每一轮质疑都带 `focus_key`（即 rubric 维度），收尾产出未解决条目，修订判定产出被质疑处是否变化。这些数据已在库中，缺的只是聚合层。

### 12.10.1 第一层：维度命中率（不调用模型）
按 `focus_key` 分组统计：该维度被质疑人数 / 其中留有未解决条目的人数 / 这些人中未修订的人数。

- 输出为教师可直接用于讲评的陈述，例如「本次『论据支撑』维度 28 人被质疑，21 人未答住，其中 15 人被质疑处一字未动」
- 挂在作业看板既有响应中，与改写程度分布并列
- 不调用模型，结果可复现、可进导出、可进跨作业趋势

**已知偏差：维度标签可信，标签下的内容没有校验。**

`focus_key` 由服务端按轮次计算后写入回合记录，模型碰不到它——所以同一份作业里每个学生的第 N 轮一定挂同一个维度标签，这一点没有随机性。维度只是拼进 user message 的一行提示，模型听不听是它的事；回合输出的校验只有两条（JSON 能否解析、`quote` 能否锚回原文），**质疑内容与 `focus_key` 是否对得上，一个字都没查**。

于是本节的聚合建立在一个未度量的假设上：模型确实按提示落在了指定维度。样本大了会向均值回归，但偏差的大小目前未知。

- 不为此加自动校验——判「这句质疑属于哪个维度」本身又是一次模型调用与一次可能的误判，代价高于收益
- 处置方式是**抽样人工核对**：验收与每学期首次真实使用时，抽查几轮质疑是否落在勾选的维度上
- 若抽查显示偏离严重，先改提示词，不改判定链路
- 同一维度下每个学生被问的**问题内容必然不同**（每轮必须引用学生自己的原文），这是设计意图不是偏差：统一的是维度，不是问题

### 12.10.2 第二层：未解决点归纳（教研分析）
把该作业下全部未解决条目连同各自 `focus_key` 一次性交给模型，归纳为 3~5 类「本班普遍站不住的论证类型」，每类给出类型名、命中人次、两条脱敏原文样例、一条课堂讲评建议。

四条约束，缺一条本功能即不可用：

- **必须缓存**：沿用现有分析缓存机制，输入哈希不变不重算，否则教师每次刷新都触发一次模型调用
- **必须设最小样本门槛**：完成质疑的学生少于 5 人时不出结论，显示样本不足。少量样本的归纳是噪声，而教师会当真
- **必须脱敏到无法回指**：只传文本与维度，不传姓名学号；样例展示不得使学生在课堂上被认出。这是教师敢把它用于公开讲评的前提
- **只报频次，不作评价**：允许「以个例代替普遍规律，出现 14 人次」，禁止「本班论证基础薄弱」这类对班级的评价性结论

由教师主动触发生成，不随看板自动生成。

### 12.10.3 第三层：跨作业趋势（后续）
同一班级在多次作业间各维度未解决率的走向。这是唯一能回答「这学期的教学是否起效」的指标，需作业量积累后才有意义，首期只需保证数据结构支持回溯。

### 12.10.4 闭环要求
分析结果必须能直接变成下一轮的教学配置，否则它只是一张看完即走的图表。

- 第一层每个维度旁提供「设为下次作业的质疑焦点」，直接写入新建作业的质疑配置

## 12.11 学生侧的透明边界
目标：回答“系统记录了学生什么、其中哪些该让学生知道”。

### 12.11.1 两件被混成一件的事
过程数据的透明有两层，此前的实现把它们当成了一层：

- **采集范围**：记录了哪些行为、谁能看到。
- **判定口径**：指标怎么算、多少算达标。

两层的处置方向相反，而原先的实现恰好反了：学生端画像页会连同两个合成指数的公式与阈值一起返回（修订比 30% 记满、跨度 3 天、提问 10 条），而“写作过程被记录”这件事在界面上从未说过一句。等于把刷分路标给了学生，却没告诉他这里在采集数据。

### 12.11.2 阈值只给教师
`index_formula` 从学生端画像响应中移除，只保留在教师端。学生看得到自己的指标值与趋势，看不到达标线。

两端用途不同：教师要拿这一页向学生解释分数，没有公式就是黑箱；学生拿到公式则等于拿到刷分说明书——把三个数字凑够即可，而凑数字与写好文章无关。

同一条判断也决定了反思质量的口径。该维度原先按反思四段的字符数折算（写满 60/20/60/40 即满分），只数字数不看内容，且目标字数随公式一并下发给学生。字数不是质量的代理变量，因此该算法整体删除，改由教师批改时给 1—5 分（见 12.6）。代价是未批改的提交该维度为空——空值优于假分。

### 12.11.3 告知只说采集范围
学生在加入班级页、作业写作区与个人写作区各看到一段告知：记录哪些行为、作业写作教师可见、个人写作空间教师不可见（在个人写作区只说后一条）。告知中不出现任何指标名与阈值。

告知不会带来新的规避手段——学生本来就在这个界面里写字和对话，知道被记录并不多出一种伪造方式。而“过程被看见”这一教学机制成立的前提正是学生知道自己被看见；不告知的话，采到的根本不是被看见之后的写作行为。

## 12.12 教研数据导出（管理员）
目标：让教改项目拿到可直接做统计分析的数据，而不是靠教师界面截图。

### 12.12.1 与班级进度导出的区别
班级详情页的 CSV 是给教师看谁交了没交的：姓名邮箱明文、七列、零过程指标。教研要的是另一份东西，因此另开接口，而不是往那份上加列——两者的读者、粒度与脱敏要求都不同。

### 12.12.2 需求
- 挂管理员权限，教师够不到
- 可按班级与提交时间范围筛选
- `submissions.csv`：每份提交一行，含全部过程/协作/质疑指标与四项数据完整度
- `round_progress.csv`：退回—重交之间的改动幅度、分数变化与响应时长
- `reflections.csv`：反思四段字数与教师给的反思质量
- `README.txt`：导出时间、算法版本与代码校验和、班级范围、行数，以及各指标的信任口径
- 反思原文默认不导出，显式开启才带

### 12.12.3 两条硬约束
- **假名化**：`pseudo_id` 由账号 id 经服务端密钥 HMAC 得到，同一个人在多次导出中稳定为同一 id，但反推不回账号；导出不含姓名与邮箱。
- **每行携带算法版本与代码校验和**：画像算法会改版，口径改动会提升 `metric_version`。跨学期取的两批数据只要版本不同就不可比；带上版本号至少能让分析者发现这件事，不带就是悄悄得出一个错误结论。

### 12.12.4 空值语义
空值一律留空、不填 0。未批改的提交反思质量为空，未开启读者试读的作业质疑指标为空——那是“不适用”而不是“表现差”，在统计上必须与 0 分得开。

## 15. 非功能需求
- 权限隔离明确：教师只能访问自己课堂与作业相关数据；个人写作空间对教师不可见
- 数据留痕可靠：写作版本、来源片段、提交记录不可无故丢失，且不设自动清理期限
- 留痕信任层级清晰：服务端权威数据与客户端上报数据不得在教师界面上混同解释，且口径必须与数字同屏呈现
- 画像可复现：相同证据与相同算法版本必须得到相同输出哈希；发布新算法必须提升指标版本
- 学生侧透明边界固定：采集范围必须在界面上告知，判定阈值不得进入学生端响应
- 对外数据集必须假名化并逐行携带算法版本，不含姓名与邮箱
- 页面响应稳定：教师端列表页和 submission detail 需保持顺畅
- 多端兼容：桌面端优先，同时兼容移动端基础访问
- i18n 兼容：新增文案需进入现有国际化机制
- 可扩展性：后续可继续叠加 rubric、批量操作、教研分析

## 16. 风险与约束
## 16.1 产品风险
- 若教师端 Overview 不足够“待办导向”，教师仍会迷失在页面间跳转
- 若评阅动作太重，教师不会真正把系统作为日常批改入口
- 若来源高亮解释不清，教师可能误解 AI 痕迹数据
- 质疑环节若不给正面收尾，学生的体验只是“被怼一顿”，会持续跳过，功能空转
- 质疑读者若沾染辅导口吻、或辅导助手沾染质疑口吻，学生将分不清 AI 是帮手还是考官，两个角色同时失效
- 反思质量改由教师给分后，教师若普遍不批改，画像的 AI 协作维会长期为空，该维度事实上失效
- 采集告知会让部分学生刻意表演写作过程；这是「被看见」机制的固有代价，不告知则采到的数据同样不是自然行为

## 16.2 技术风险
- 写作版本和 provenance 数据会持续增长，且不设清理期限，需要控制存储和查询成本
- 来源片段与澄清追问的答案侧由客户端上报，理论上可伪造，不能作为学术诚信的唯一判据
- 聊天、写作、版本、提交是跨模块联动，后续改动容易引起回归
- 学生写作页同时承载聊天与编辑，复杂度高于普通表单页
- 教育表结构一律由 Alembic 负责，画像相关迁移是有意不兼容的前向迁移，只允许证据表为空时执行

## 16.3 组织风险
- 若没有明确区分“通用聊天能力”和“教学流程能力”，需求会持续发散

## 16.4 待定问题
- 学生注册后的审批形态未定：注册即用、教师审批还是管理员审批
- 缺少班级转交能力，导致仍拥有班级的教师无法降级或撤销教学身份
- 评分维度跨作业复用的形态未定：作业级模板、课堂级模板还是平台级量纲库
- 反思质量在教师未批改时是否需要替代口径未定：当前一律留空，代价是画像要等批改才完整

### 16.4.1 已否决：AI 判定「学生是否真的回应了质疑」

片段级判定（12.9.8）只回答「被质疑的那处变没变」，回答不了「这次修改是否真的回应了质疑」。曾考虑引入 AI 判定补上后者，**2026-09-09 定案不引入，且不再作为待定问题保留**。三条理由，任何一条单独成立即足以否决：

**一、AI 的角色会崩塌。** 本环节最关键的设定是 AI 是**读者，不是判官**。读者说「我没看懂你这句凭什么成立」，这句话在认识论上不可反驳——学生没法说「你其实看懂了」，唯一出路是把话说清楚。这正是写作教学要的位置：把学生从「应付评分者」推到「说服读者」。AI 一旦说出「你没有真正回应我的质疑」，它就成了判官，而判官的结论天然可反驳，学生完全有资格说「我回应了，是你没读懂」——**而且他有时是对的**。争议的裁决权于是回到教师手上，教师负担不减反增：原本只需看三栏自己下判断，现在要先推翻或背书 AI 的判断，再面对申诉。

**二、判定的落点是错的。** 判定发生在提交那一刻，学生已经离场；结论写进教师端的提交详情，学生永远看不到、也永远无法回答。一个学生看不见、无法答辩、只在教师那边生效的负面结论，拿走了误判的全部代价，却没有任何教学收益——**反馈没有落在学习者身上**。要有教学价值就必须回到学生面前，一旦回到学生面前，第一条的申诉问题全面爆发。两条路都不通。

**三、可判定即可优化。** 「真回应」一旦成为机器可检的目标，学生会很快学会「在这个模型眼里回应长什么样」，大概率是复述质疑 + 加限定词 + 塞一个具体数字。产品于是教会了回应的**形式**，而不是思考。对照之下，片段级判定不怕这个：它不做任何质量宣称，只说「这句话变了」——事实无法被优化成表演，评价可以。

**与既有决定的一致性**：这与「不做 AI 打分」「不把糊弄做成系统判定」「留痕可伪造但不自动抓人」是同一条线。引入本判定将是第一处破例，且是在最容易引战的地方破例。

**遗留缺口的处置**：片段级判定挡不住「在被质疑那句里改两个无关的字」。这个缺口**接受它存在**，不由系统补——

- 缺口目前几乎无人利用：`revisionByTurn` 只往教师端传，学生端从头到尾看不到「已修改 / 未修改」，不知道判定的存在，也就没有优化它的动机
- 三栏并排本就是这个缺口的补丁：教师看到「原文」与「最终稿」几乎一模一样时，自己就能判断这是敷衍
- 是否改由「答不住就原地追问」的机制承接，**待真实课堂观察后再议，形态未定**（见 12.9.11 及其杠精风险与三条护栏）。不得把本条否决当作把该需求挪去 12.9.11 实现的许可

**重新讨论的触发条件**（留一个可证伪的口子，免得本条变成教条）：真实课堂跑过几轮后，若教师普遍反馈「三栏我看不出学生到底回应没回应」——不是嫌麻烦，是真的判断不了——那说明证据呈现不够，**先改呈现**（如片段前后各带一句上下文）；改到底仍不行，再谈判定，且必须以「读者追问」而非「结论字段」的形态落地。

## 17. 核心指标
## 17.1 北极星指标
- 完成一次完整教学闭环的作业数

定义：
- 教师创建作业
- 至少一名学生提交
- 教师完成评阅保存

## 17.2 过程指标
- 教师创建课堂数
- 课堂邀请码加入成功率
- 作业创建数
- 作业提交率
- 待评转已评转化率
- 平均评阅时长
- 退回修改率
- reflection 填写完成率
- 来源数据记录成功率
- 质疑环节完成率（完成 / 跳过）
- 质疑后正文修订率：完成质疑的提交中，收尾之后正文发生实质修改的比例
- 反思质量评分覆盖率：已批改提交中给出 1—5 分的比例

## 18. 一句话产品结论
RightWrite 不是一个“给教育场景套壳的聊天工具”，而是一个围绕教学写作闭环构建的 AI 教学工作台。

其核心价值不在“能聊天”，而在：

`能组织任务、能记录过程、能支撑评阅、能沉淀教学证据。`
