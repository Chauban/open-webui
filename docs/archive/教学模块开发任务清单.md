## 2. 任务分期总览

### Phase 1：结构稳定与体验收口
目标：
- 统一教师教学区信息架构
- 稳定页面头部和导航体验
- 为后续批改体系预留入口

### Phase 2：批改闭环与作业生命周期
目标：
- 让教师可以真正处理提交
- 让作业具备持续管理能力

### Phase 3：进度追踪与规模化运营
目标：
- 提升班级管理效率
- 补齐班级和学生维度的数据管理

## 5.2 学生长期表现视图 —— 已完成（学生成长画像）
### 任务说明
支持教师从学生视角看趋势，而不只看单次提交。

范围已确定并落地为**学生成长画像**，教师端与学生端共用同一视图与同一套指标
（教师 `/teacher/classrooms/[id]/students/[userId]`、学生 `/me/writing/growth`）。

### 前端任务
- [x] 教师端学生详情页重做为画像页；学生端新增「我的成长」入口
- [x] 产出维：得分、rubric 各维、篇幅的时间序列
- [x] 过程维：过程投入指数、修订深度、有效写作时长、临交突击占比、开工提前量
- [x] AI 协作维：协作指数、AI 占比、消化度、提问数、反思质量
- [x] 轮次进步、AI 用途分布与迁移、规则生成的结论

### 后端任务
- [x] `GET /teacher/classrooms/{id}/students/{userId}/profile`
- [x] `GET /me/writing/profile`

### 设计决定（已定，勿回退）
- 教师评分没有统一满分，产出维只呈现原值与趋势，**不折算成任何指数**
- 两个合成指数只由有界比率构成，构成公式随接口返回（`index_formula`）
- 风险信号（突发插入、疑似未标注导入）只展示，**不进成长指数**
- 过程维用修订深度而非版本数：一个版本只是一次自动保存

## 7. 推荐实施顺序
建议按以下顺序推进：

1. 教师端结构统一
2. Review 一级页上线
3. Overview 待办化
4. submissions 状态位
5. submission 批改能力
6. 作业生命周期管理
7. rubric 与退回重交
8. 班级进度和批量能力

原因：
- 先做结构，避免后续功能接入时继续混乱
- 再做入口，让批改有落点
- 然后做真正的处理闭环

## 8. 最小可上线范围建议
如果需要先做一个可上线版本，建议最小范围为：
- Review 一级页
- Overview 待办化
- submissions 状态位
- submission 评分与评语

做到这一步，教师端就能从“看数据”升级到“完成处理”。

## 9. 一句话结论
教学模块的开发任务应优先围绕两件事推进：

- 先把结构做稳定
- 再把批改闭环做出来

其他如班级进度、批量导入、导出能力，都应建立在这两个基础之上。
