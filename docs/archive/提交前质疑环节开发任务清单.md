# 提交前质疑环节（Challenge Round）开发任务清单

对应 `PRD.md` 12.9 与 13.20 / 13.21。目标是把 AI 从单一辅导助手扩为「辅导助手 + 质疑读者」两个角色。

创建时间：2026-09-06
状态：**全部完成**。P0 后端 `e1434c910`、P1 学生端 `7681b12be`、P2 教师端 `2033d31b9`、P3 画像与文档 `0efcc64af`，分支 `worktree-challenge-round-p0` 已推送 origin。

> ⚠️ **升级前必须先清画像证据数据，否则后端起不来。** P3 把 `evidence_schema_version` 升到 `2026-09-06.1`，迁移 `b1e6d4a8c3f7` 会在证据表非空时抛错阻止升级（这是既有约定，不是 bug）。需要清空：`student_profile_rollup_projection`、`student_profile_aggregate_projection`、`profile_projection_outbox`、`profile_metric_projection`、`submission_review_event`、`profile_evidence_snapshot`。班级、作业、提交、写作版本都不受影响。

实现与原计划的四处偏差（都是有意的）：
- **T15 换了实现方式**。原计划用 `editor_operation` 的客户端时间戳比对质疑结束时间，实际改成比对两份服务端快照：发起质疑时冻结的 `source_version` vs 最终提交正文。原方案既依赖客户端时钟（和服务端时间没有可比性），又只统计上报成功的编辑。新方案是服务端权威数据，因此**不需要 analysis.py 的缓存机制，也不用提逻辑版本**——结论在提交时算好冻进 `stats_json.challenge.revision`。PRD 12.9.6 / 12.9.7 已同步更正。
- **T14 没有复用 `EduEvidenceDisclaimer`**。那句免责说的是「学生浏览器记录，可能不完整或被绕过」，而质疑回合三类数据全在服务端权威层，挂上去会把权威数据错误降级，正好违反 12.9.7「不得混同」。改成一句准确的说明。
- **T16 的画像位置改了**。原计划没写放哪一维，实际放在写作过程维而不是 AI 协作维：质疑读者不是帮手，并进「AI 协作」会把两个刻意分开的角色又混回去。
- **`ChallengeSettings` 放在评分维度编辑器之下**，不是紧贴 `CoachingStyleSelector`。焦点选择依赖已定义的维度，顺序反了会让教师在维度还没填时先看到焦点按钮。两个控件被隔开后，说明文案里补了一句和辅导风格的对比。

已知环境问题（非本功能引入）：`node_modules/@testing-library/svelte`（5.2.8）缺 `src/vitest.js`，而 `vite.config.ts` 的 `svelteTesting()` 插件会把它挂成 setupFile，导致**所有** dom 测试连收集都失败。修复方式是重装该依赖。本次验证组件测试用的是临时 vitest 配置，已删除，未改动仓库配置。

### T3 质疑提示词配置
文件：`backend/open_webui/config.py`、`backend/open_webui/routers/configs.py`

**验收**：管理员在管理面板改写措辞后，新发起的质疑立即生效。

### T4 回合引擎
新文件：`backend/open_webui/services/education/challenge.py`

- `start_session(assignment, writing_session, user)`：冻结当前正文版本为 `source_version_id`，落 session，生成第 1 轮质疑
- `submit_response(session, turn_no, text)`：存回应；未达 `planned_rounds` 则生成下一轮，已达则转 `close_session`
- `close_session(session)`：调用 closing 提示词，产出 `{"stood": [...], "unresolved": [...]}` 存入 `closing_summary_json`，status 置 `completed`
- **回合数由本模块的代码控制，不由提示词控制**。每轮调用的输入 = 正文快照 + 本轮 focus 维度（含 label 与配分）+ 前几轮的质疑与回应
- 焦点维度按轮次轮转：`focus_keys[(turn_no - 1) % len(focus_keys)]`
- 模型选择：复用学生写作区当前 active chat 的模型；取不到则用系统默认模型

**验收**：单测覆盖「3 轮后必然进入 closing」「第 4 次 respond 被拒绝」「focus_keys 只有 1 个时三轮都打同一维度」。

### T5 API 路由
文件：`backend/open_webui/routers/education.py`

- `POST /assignments/{assignment_id}/challenge/start` → 返回 session + 第 1 轮质疑
- `GET  /assignments/{assignment_id}/challenge/current` → 恢复未完成 session（刷新页面不丢进度）
- `POST /challenge/{session_id}/respond` → 返回下一轮质疑或收尾清单
- `POST /challenge/{session_id}/skip` → status 置 `skipped`
- `PATCH /challenge/{session_id}/checklist` → 保存勾选状态
- `GET  /submissions/{submission_id}/challenge` → 教师读回合与派生指标
- 权限：前五个仅本人；最后一个仅该作业所属教师与管理员
- 作业未启用质疑时，start 返回 400

**验收**：学生 A 无法读 / 写学生 B 的 session；非本作业教师读 submission 质疑返回 403。

### T6 提交时冻结
文件：`backend/open_webui/routers/education.py`（`submit` 附近，参照现有 `stats["coaching"]` 的写法）

- 把本轮 `challenge_session_id`、status、实际完成回合数、以及当时生效的质疑提示词原文一起写进 `submission.stats_json["challenge"]`
- 理由与 coaching 一致：管理员随时可改措辞，已交的那一轮记录不能跟着变

**验收**：提交后改写 `education.challenge_prompts`，已提交记录里的原文不变。

### T7 后端测试
文件：`backend/open_webui/test/apps/webui/routers/test_education_smoke.py`

- 完整流程：启用质疑的作业 → start → 3 轮 respond → closing → 提交 → 教师读到回合

- 未启用质疑的作业提交流程不受任何影响（回归）
- 措辞冻结测试（对照现有 coaching 那条的写法）

## 明确不做

- 不做 AI 打分或等级预测（会架空教师评分权威，学生转向对着 AI 刷分）
- 不做角色下拉菜单让学生自选（没人会主动选难受的那个）
- 不把质疑塞进左侧聊天框（两种对话契约相反，必然互相污染）
- 不给 `coaching_style` 增加质疑档位（学生会分不清 AI 是帮手还是考官）
- 不做无限回合
- 不拦截「学生切回左侧让辅导助手代答质疑」——该行为会进 prompt timeline，教师可见，暴露即可
- 维度自查 / AI 批改角色本期不做，待质疑环节跑通并有真实课堂反馈后再评估
