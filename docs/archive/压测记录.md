# 历史压测记录

> 2026-10-10 汇总既有压测说明、执行状态和哈工深实例记录。以下描述当时的测试条件与观察结果，不代表当前承载能力。

运行方法和参数统一见 [压测工具](../../scripts/loadtest/README.md)，部署环境详见 [现网记录](../deployment/部署流程.md) 和 [哈工深记录](../deployment/哈工深部署流程.md)。

## 测试方法

- 服务器容量测试使用 OpenAI 兼容的模拟模型，覆盖鉴权、聊天写入、流式转发和 Socket.IO 推送，排除真实模型商限流的影响。
- 模拟回复设为 400 token、25 token/秒、首 token 延迟 600 毫秒，每次回复约 16.6 秒。
- 真实模型诊断测试经本机后端生成诊断提示词并转发请求，检查返回是否能解析成修改结论；它测量模型商并发及后端转发，不等同于服务器容量测试。

## 2026-09-09：环境与工具核查

现网使用 4 个 uvicorn worker，总内存 7623 MB，systemd 记录的运行内存峰值为 3.9 GB。当时估计每个 worker 导入 torch 约占 874 MB，优先关注内存；这是测试前判断，后续容量实测发现主要瓶颈是 CPU。

模拟模型的模型列表、流式与非流式回复已在本地验证，流式包含 role、content、finish_reason、usage 和 `[DONE]`。k6 v2.2.0 的 `inspect` 能解析聊天、Socket.IO 和页面接口三个场景。本轮记录没有服务器容量实测结果。

## 2026-10-03：真实模型诊断并发

模型为 DeepSeek V4.1 Flash（接口名 `deepseek-flash`），使用固定文献综述样稿和评分维度，同时发起 60 次第一次通读诊断。

| 指标       | 结果  |
| ---------- | ----- |
| 请求成功   | 60/60 |
| 结论可解析 | 60/60 |
| 耗时中位数 | 29 秒 |
| P90        | 64 秒 |
| 最长耗时   | 85 秒 |

这是当时模型及账号条件下的结果；换模型、账号或服务配置后需要重新测量。

## 2026-10-04：哈工深服务器容量

环境为 2 核 CPU、8 GB 内存、4 个 worker，模拟模型每次回复约 16.6 秒。实际使用管理员浏览器会话发起对话、Socket.IO 长连接及每秒 3 批页面接口请求。

`stream_delta_chunk_size` 控制攒多少 token 再推送一次。记录中的性能变化如下，未记录的指标用“—”表示：

| 推送批量          | 同时等待回复人数 | 回复中位数 | 回复 P95 | 页面接口表现                  |
| ----------------- | ---------------- | ---------- | -------- | ----------------------------- |
| 默认每 token 推送 | 15               | —          | —        | P95 20.8 秒，CPU 已满         |
| 默认每 token 推送 | 30               | 32 秒      | —        | —                             |
| 默认每 token 推送 | 60               | 56 秒      | 82 秒    | 中位数 20 秒                  |
| 10 token          | 15               | 17.0 秒    | —        | P95 0.59 秒                   |
| 10 token          | 60               | 20 秒      | —        | —                             |
| 30 token          | 60               | 18.0 秒    | 19.6 秒  | 中位数 2.2 秒，P95 仍约 20 秒 |

测试期间内存可用量至少 3.9 GB、PostgreSQL 连接不超过 50、服务无重启、对话无失败。CPU 主要消耗在逐 token 处理及推送；记录中 worker 各约占 30%–55%，Nginx 约占 27%。批量推送降低了回复耗时，但峰值 CPU 仍可能占满，页面请求的高分位延迟仍较高。

当时已将 `deepseek-flash` 的 `stream_delta_chunk_size` 设为 30，回复呈现约半秒一次的分段输出。该调整属于当时实例设置，不是所有实例的代码默认值。原记录提出升配、非流式诊断或错峰作为后续方向，尚不能据此声称这些方案已实施或验证。

## 测量限制与排障结论

- 浏览器测试使用单一管理员账号，不能证明完整学生身份流程或多账号并发行为。Chrome 单页约只能建立 127 条 WebSocket，目标 200 条连接的场景实际未压满。
- k6 `chat_stream_duration` 是整次请求耗时，不是首 token 延迟。家宽到香港的网络延迟计入 HTTP 耗时，不能将它直接解释为服务器处理时间。
- k6 的 Socket.IO 场景手工处理 Engine.IO 协议帧，协议版本变化后需重新检查脚本。
- v0.11 的聊天接口校验 `chat_id` 归属，编造的 id 会在模型调用前返回 404。压测脚本需先为每个虚拟用户创建自己的聊天。
- 带 `chat_id` 的模型流由后端处理并经 Socket.IO 推送，HTTP 响应可能为 `null`；当时脚本使用 HTTP 200 且耗时大于 3 秒作为模拟模型场景的通过条件。
- 模拟模型应按测试账号配置访问权限；不可把无模型权限产生的错误当作性能问题。停止服务时，`pkill -f` 可能匹配到含相同脚本文字的 SSH 命令自身。

旧安装命令、临时待办、服务故障快照及会话授权表述已从维护文档移除，原始版本仍可从 Git 历史追溯。
