# 并发压测（方案 B：假模型端点）

目的：确认腾讯云香港那台 **2 核 8G** 撑不撑得住 100–200 名学生，且**不花一分钱模型费**。

思路是在服务器上跑一个 OpenAI 兼容的假模型（`mock_llm.py`），按固定节奏吐 SSE token。
压测打进去的请求会走**完整的真实路径**——鉴权、Postgres 写入、worker 占用、
流式转发、Socket.IO 广播——唯独最后一跳的模型是假的。这样测出来的瓶颈是服务器的，
不是上游模型商限流的。

## 文件

| 文件 | 跑在哪 | 作用 |
|---|---|---|
| `mock_llm.py` | 服务器 | 假模型端点，只用标准库，无需装任何依赖 |
| `loadtest.js` | 本机 | k6 压测脚本，三个场景并发 |

---

## 零、先确认一件不用压测就能查的事

**worker 数量可能比 CPU 更早成为瓶颈。** 每个 uvicorn worker 光 torch 就占 874MB PSS
（见 `部署流程.md` 第五节），8G 内存下这是硬约束。先查清楚现在开了几个：

```bash
systemctl cat rightwrite | grep -iE 'workers|ExecStart'
ps -eo pid,rss,cmd --sort=-rss | grep -i uvicorn | head
free -m
```

如果 worker 数配得不对，压出来的是一个错误配置的极限，白测。

## 一、服务器侧：启动假模型

```bash
# 1. 从本机上传（在本机 PowerShell 里跑）
scp -i RightWrite.pem loadtest/mock_llm.py ubuntu@43.161.198.209:/tmp/mock_llm.py

# 2. 登录服务器，后台启动（按既有规范用 nohup，见 部署流程.md 第六节踩坑 9）
ssh -i RightWrite.pem ubuntu@43.161.198.209
nohup python3 /tmp/mock_llm.py > /tmp/mock_llm.log 2>&1 &

# 3. 验证
curl -s http://127.0.0.1:9099/v1/models
curl -s http://127.0.0.1:9099/health
```

只监听 `127.0.0.1`，**不对公网暴露**，不需要动防火墙。

可调参数（启动前 `export`）：

| 变量 | 默认 | 含义 |
|---|---|---|
| `MOCK_TOKENS` | 400 | 每次回复吐多少 token |
| `MOCK_TPS` | 25 | 每秒吐几个 → 默认一次回复约 **16 秒** |
| `MOCK_TTFT_MS` | 600 | 首 token 延迟 |
| `MOCK_PORT` | 9099 | 监听端口 |

16 秒一次回复是刻意设的——真实模型就是这个量级，**流持续的时间越长，同时被占住的
worker 协程越多**，这正是要测的东西。想加压就调大 `MOCK_TOKENS` 或调小 `MOCK_TPS`。

## 二、服务器侧：把假模型接进去

在网站的 **管理面板 → 设置 → 外部连接 → OpenAI API** 里新增一条：

- URL：`http://127.0.0.1:9099/v1`
- Key：随便填（`mock` 即可，脚本默认不校验）

保存后模型列表里会出现 **`loadtest-mock`**。

⚠️ **接着必须设置模型可见性**：到 管理面板 → 模型 → `loadtest-mock`，把访问控制设为
公开（或加上要用来压测的那几个账户）。否则压测账户拿不到这个模型，`/api/chat/completions`
会直接返回 `Model not found`——按 `CLAUDE.md` 的排障优先级，这类问题永远先查权限。

## 三、本机：装 k6

```powershell
winget install k6 --source winget
# 或 choco install k6
k6 version
```

## 四、本机：跑

先准备几个能登录的测试账户（生产上还是内测期，账户可以自己建）。
`EMAILS` 里给几个就用几个，脚本会按 VU 编号取模复用。

```powershell
$env:BASE_URL   = "https://rightwrite.cc"
$env:EMAILS     = "t1@example.com,s1@example.com,s2@example.com"
$env:PASSWORD   = "你的测试账户密码"
$env:MODEL      = "loadtest-mock"

# 第一档：轻负载探路
$env:CHAT_VUS = "5"; $env:SOCKET_VUS = "20"; $env:DURATION = "2m"
k6 run loadtest\loadtest.js
```

**建议的加压梯度**（每档跑完看一眼服务器再决定要不要进下一档）：

| 档 | `CHAT_VUS` | `SOCKET_VUS` | 对应现实 |
|---|---|---|---|
| 1 | 5 | 20 | 探路，确认脚本本身没问题 |
| 2 | 10 | 50 | 一个班在上课 |
| 3 | 25 | 100 | 两个班同时用 |
| 4 | 50 | 200 | 全量学生 + 半数在同时提问 |

`CHAT_VUS` 是**同时在等模型回复**的人数，不是总人数——真实课堂里绝大多数人在写字
或读页面，所以 `SOCKET_VUS` 才对应"开着页面的总人数"。第 4 档的 50 已经相当激进。

## 五、压的时候盯什么

另开一个 ssh 窗口：

```bash
# CPU 与内存（重点看 %CPU 是否长期贴 200%，以及 available 内存）
top -b -d 2 | head -20

# 应用是否被 OOM killer 干掉过
sudo journalctl -u rightwrite -n 50 --no-pager
dmesg -T | grep -i 'killed process' | tail

# Postgres 连接数（默认上限 100，worker 多了很容易撞）
sudo -u postgres psql -c "select count(*), state from pg_stat_activity group by state;"

# Nginx 有没有开始 502/504
sudo tail -f /var/log/nginx/error.log
```

判断标准：
- **CPU 贴满 200% 且 p95 飙升** → 2 核不够，需要升配
- **内存 available 掉到几百 MB** → worker 数太多，先减 worker 而不是升配
- **`pg_stat_activity` 接近 100** → 连接池配置问题，不是机器问题
- **502/504** → 上游超时或 worker 全被流式请求占死

## 六、收尾（重要，别忘）

```bash
# 1. 管理面板里删掉那条 OpenAI 连接（否则以后模型列表里一直挂着假模型）
# 2. 停掉 mock
pkill -f mock_llm.py
rm /tmp/mock_llm.py /tmp/mock_llm.log
```

压测产生的聊天记录可以直接删——生产库内测期除账号外都可清（见 `部署流程.md`）。

## v0.11 之后的变化（2026-10-04 哈工深压测踩到）

- `/api/chat/completions` 会校验 `chat_id` 归属，编造的 id 直接 **404 "Something went wrong"**（耗时一两百毫秒，一看就是没到模型）。`loadtest.js` 已改为每个 VU 先 `POST /api/v1/chats/new` 建自己的对话再反复提问。
- 带 `chat_id` 时服务端自己读完模型流、落库、经 Socket.IO 推送，**HTTP 只回 `null`**。所以成功判据改为「200 且耗时 > 3 秒」，不再检查 SSE 文本。
- 管理面板加假模型连接时「认证方式」选**无**，不用填 Key；模型访问控制只授予压测账号（`POST /api/v1/models/create` 带 `access_grants`），不必设公开。删除：`POST /api/v1/models/model/delete {id}` + 连接设置里删连接。
- 服务器上 `pkill -f mock_llm.py` 别和含 `mock_llm` 字样的命令写在同一条 ssh 里：`-f` 会匹配到 ssh 自己的 bash 命令行把会话杀掉（exit 255）。
- 没法在本机跑 k6（例如账号密码不能交给代跑的人）时，可以在**已登录管理员的浏览器页面**里用 JS 发同样三类负载（对话流 / WebSocket 长连接 / 页面接口），走的是同一条服务器路径；局限是单账号，且 Chrome 单页最多撑到约 127 条 WebSocket。

**调优旋钮**：模型参数 `stream_delta_chunk_size`（或全局 env `CHAT_RESPONSE_STREAM_DELTA_CHUNK_SIZE`，需重启）。默认每 token 推一次，CPU 是瓶颈；哈工深实测 =30 时 60 人同时对话的回复耗时从中位 56 秒降到 18 秒。数据见 `哈工深部署流程.md` §五。

## 已知局限

- **测不出 TTFT（首 token 延迟）**。k6 的 `http.post` 会等整条 SSE 流收完才返回，
  所以 `chat_stream_duration` 是**整条流的总时长**，不是首字延迟。要单独测首字得用
  `xk6-sse` 自行编译 k6，为了一个指标不值得。
  用户体感的"卡不卡"看 `browse` 场景的 p95 更直接。
- **家宽到香港的延迟会计入 `http_req_duration`**。看的是**趋势和是否崩**，不是绝对值。
  如果第 3、4 档出现"到底是网络还是 CPU"的模糊地带，再考虑同区开一台按量计费小机器
  当压力机（几块钱一小时）。
- **Socket.IO 场景用的是裸 engine.io 协议帧**（`0` / `40` / `2`→`3` / `42[...]`）。
  如果哪天上游升级了 socket.io 大版本，这段要跟着改。

## 附：第一次通读的模型商并发（`diagnosis_burst.py`，不用部署）

修订初稿作业里，学生点「确认这是我的初稿」会触发一次逐项诊断（开思考，20～50 秒）。一节课几十人几乎同时点，先撞上的是**模型商的并发/限流**，不是服务器——这一层在本机就能测：脚本经本机后端的 `/api/chat/completions` 打真模型，用的是真实的诊断提示词和一份样稿，并检查每个返回能不能解析成结论表。会真实消耗额度。

```powershell
$env:WEBUI_SECRET_KEY = Get-Content open-webui\backend\.webui_secret_key
$env:RW_ADMIN_EMAIL = '<管理员邮箱>'; $env:RW_ADMIN_PASSWORD = '<密码>'
open-webui\backend\.venv\Scripts\python.exe loadtest\diagnosis_burst.py --n 60 --model deepseek-flash
```

2026-10-03 结果：DeepSeek-V4.1-Flash 60 并发 **60/60 成功、全部可解析**，中位 29s、P90 64s、最长 85s。服务器容量（2 核 8G、4 worker）仍要在机器上用上面的 k6 压。
