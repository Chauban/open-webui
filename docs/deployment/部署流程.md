**为什么是 8GB 而不是 4GB**：应用实测常驻 3.5GB（原因见排障第 5 条）。4GB 会直接 OOM。

### systemd `/etc/systemd/system/rightwrite.service`

```ini
[Service]
User=rightwrite
WorkingDirectory=/opt/rightwrite/app/backend
EnvironmentFile=/opt/rightwrite/rightwrite.env
Environment=HOME=/opt/rightwrite
ExecStartPre=/opt/rightwrite/migrate.sh
```

- `Environment=HOME=...` 必须显式设置：systemd 的 `User=` 不会自动设 HOME，部分库依赖它。

### Nginx `/etc/nginx/sites-available/rightwrite`

## 六、排障：已踩过的坑

### 1. 多 worker 并发跑 Alembic → 全表回滚

**现象**：启动后报 `relation "config" does not exist`，而数据库里一张表都没有。

**原因**：`config.py` 在 import 末尾触发 `run_migrations()`（不是 uvicorn 的行为，是**模块导入副作用**）。4 个 worker 各导入一次 = 各跑一遍迁移，Postgres 事务互撞后整批回滚。更麻烦的是 `run_migrations()` 用 `except Exception` **吞掉异常**，日志里只留一行 error，看起来像「启动了」。

**解法**：`ExecStartPre=/opt/rightwrite/migrate.sh` 单进程先跑完，并设 `ENABLE_DB_MIGRATIONS=false` 让 worker 不再碰。

**不能直接调 alembic CLI**：`migrations/env.py` 会反向 import `open_webui.config`，而 config.py 自身触发迁移，直接调会形成循环导入（报 `cannot import name 'Calendar' from partially initialized module`）。正确做法是在单进程里 `import open_webui.config`，靠导入副作用完成迁移。

### 2. 多 worker 并发播种默认配置 → 唯一键冲突

**现象**：`duplicate key value violates unique constraint "config_pkey1"`，`Key (key)=(direct.enable) already exists`。重启一次后会「自愈」（因为配置已被写入），但首次启动必失败。

**原因**：`main.py` 启动时 `seed_registered_defaults()` 批量 INSERT `config` 表。

**解法**：同上，`migrate.sh` 里 `asyncio.run(cfg.seed_registered_defaults())` 单进程播种。

### 3. Boolean 列上的 `CHECK (col IN (0, 1))` 在 Postgres 报错

**现象**：`operator does not exist: boolean = integer`，83 个迁移在同一事务里全部回滚。

**原因**：SQLite 容忍布尔与整数比较，Postgres 严格拒绝。**本地 SQLite 开发永远测不出来。**

**解法**：已在 `19d819c37` 修复（删掉冗余约束——Boolean NOT NULL 本身就只能取 true/false）。

> **今后写迁移时注意**：`submission.is_current` 是 `BigInteger`，它的 `IN (0, 1)` 是合法的；只有真正的 `Boolean` 列不能这么写。加约束前先确认列类型。

**加固**：`migrate.sh` 会比对「数据库 alembic 版本 == 代码 ScriptDirectory head」，不一致直接退出非零，systemd 拒绝启动 worker。避免带着半迁移的 schema 静默上线（那会表现为「功能莫名其妙不工作」，极难排查）。

### 4. pip 会拉 4–5GB 的 CUDA 库

**现象**：`pip install -r requirements.txt` 下载 `nvidia_cudnn_cu13`（553MB）等一堆包。**这台机器没有 GPU。**

**解法**：先装 CPU 版占位，再装 requirements：

```bash
pip install --index-url https://download.pytorch.org/whl/cpu \
            --extra-index-url https://pypi.org/simple torch torchvision
pip install -r backend/requirements.txt   # torch 已满足，CUDA 系列全部跳过
```

结果：`torch==2.14.0+cpu`，CUDA 包 0 个。

### 5. torch 仍会进内存（每 worker 874MB）

**别指望用配置关掉它。** 运行时 import 拦截追踪到的真实路径：

```
main.py → events.py → retrieval/web/utils.py
  → langchain_community.document_loaders (PlaywrightURLLoader)
  → langchain_text_splitters/__init__.py   # 无条件 import sentence_transformers 子模块
  → transformers → torch
```

跟 `RAG_EMBEDDING_ENGINE` / `BYPASS_EMBEDDING_AND_RETRIEVAL` **完全无关**——那两个开关只阻止**加载模型权重**（这部分确实有效：缓存目录保持 20K，不会去 HuggingFace 拉模型），阻止不了**库被 import**。

实测：每 worker RSS 1191MB / **PSS 874MB**（RSS 会重复计算共享的 .so，PSS 才是实数），4 worker 合计 **3.5GB**。估算容量时按 PSS 算。

要真正去掉只能改 `retrieval/web/utils.py` 的模块级 import —— 属 fork 偏离上游，每次 merge 都可能冲突，**不建议**。

### 6. Nginx 1.24 不支持 `http2 on;`

**现象**：`unknown directive "http2"`，`nginx -t` 失败。此时运行中的 nginx 仍用旧配置，网站看似正常，但**下次 reload 会失败**（包括证书续期时的 reload），是个定时炸弹。

**解法**：1.24 要写在 listen 上 —— `listen 443 ssl http2;`（`http2 on;` 是 1.25.1+ 的语法）。

### 7. certbot 卡死会留下锁

nginx 配置损坏时运行 certbot，其 nginx 插件会卡在 reload 环节不退出，持有的锁会让后续所有 certbot 操作（**包括 `certbot.timer` 的自动续期**）报 `Another instance of Certbot is already running`。

排查：`ps -eo pid,etime,cmd | grep "[c]ertbot"`。

清理时**不要**用 `pkill -f "certbot renew"` —— 这个模式会匹配到你自己的 shell 命令行，把自己杀掉。

### 8. 端口与防火墙

腾讯云轻量默认**只放行 22**。80 和 443 都要去控制台 → 防火墙手动添加，否则服务配好了外面也访问不了，极易误判成 Nginx 配置错误。

验证方法（服务器起临时监听，本机 curl）：

```bash
ssh ... 'sudo timeout 12 python3 -m http.server 80 --bind 0.0.0.0 &'
curl -s -o /dev/null -w '%{http_code}' http://43.161.198.209/     # 通=200，不通=000 超时
```

**注意**：如果本机装了 Clash/Surge 一类代理，DNS 会返回 `198.18.x.x` 假地址，测试结果不可信。判断线上状态要以服务器侧或手机流量为准。

### 9. 构建必须「先停应用 + nohup 后台跑」

装依赖、构建这类长任务，SSH 链路抖动会中断前台命令。用 `nohup ... > /tmp/x.log 2>&1 &` 起，再另行轮询日志。首次部署中 SSH 断过一次，后台任务因此毫发无损。

**但 nohup 只解决链路问题，不解决内存问题。** 2026-09-09 上线时前台直接跑 `build.sh`，应用常驻 3.5GB 叠上 vite/esbuild：

- 8GB 全打满进 swap，**load average 冲到 74**
- sshd 连 banner 都发不出来（`Connection timed out during banner exchange`），HTTPS 完全无响应
- 机器失联约 8 分钟，期间既观测不了也干预不了

没有 OOM 记录，构建自己跑完了（09:41:21 写出 `build/index.html`），但代价是整台机器等于宕机。**结论：构建前先 `systemctl stop rightwrite`**，可用内存立刻从 469MB 回到 7GB，构建不再 swap。反正 restart 本来就要断一次，停机窗口没变长。

**判断机器死活**：从本地 `curl -m 20 https://rightwrite.cc/health`，不要只依赖 SSH 能否登录。

## 九、备份

每日 03:30 由 `rightwrite-backup.timer` 触发 `/opt/rightwrite/backup.sh`，产物落在 `/opt/rightwrite/backups/`，保留 30 天。

| 内容 | 方式 |
|---|---|
| Postgres 全库 | `pg_dump --format=custom --compress=9`（支持选择性恢复） |
| DATA_DIR 上传文件 | `tar czf` |
| 完整性校验 | `pg_restore --list` + `tar tzf`，失败则整个任务非零退出 |
| 校验和 | 追加到 `backups/checksums.txt` |

**为什么要做完整性校验**：磁盘写满或中途失败会产出一个「看起来像备份的坏文件」，不验的话要到真出事时才发现恢复不了。

当前数据量很小（数据库 10MB、上传目录 216K），30 天副本占用可忽略。

### 手动操作

```bash
sudo systemctl start rightwrite-backup          # 立即备份一次
sudo journalctl -u rightwrite-backup -n 20      # 看结果
systemctl list-timers rightwrite-backup         # 看下次运行时间
```

### 恢复演练（已验证通过）

```bash
sudo -u postgres createdb -O rightwrite restore_test
sudo -u rightwrite pg_restore --dbname="<DATABASE_URL 改成 restore_test>" \
     --no-owner --no-privileges /opt/rightwrite/backups/db-<时间戳>.dump
# 比对表数 / config 行数 / alembic 版本是否与生产一致
sudo -u postgres dropdb restore_test
```

2026-09-08 实测：生产与还原库均为 **69 张表、330 行 config、alembic `a7e9c3b5d1f8`**，完全一致。

### 凭据与最小权限（重要设计）

上传用的是 CAM 子用户 `RightWriteAccount`，**只有编程访问，没有控制台登录**。绑定的自定义策略 `RightWriteBackupUpload`：

```json
{
  "version": "2.0",
  "statement": [
    { "effect": "allow",
      "action": ["name/cos:HeadBucket", "name/cos:GetBucket"],
      "resource": ["qcs::cos:ap-hongkong:uid/1301304366:lhcos-36974-1301304366/*"] },
    { "effect": "allow",
      "action": ["name/cos:PutObject", "name/cos:InitiateMultipartUpload",
                 "name/cos:ListMultipartUploads", "name/cos:ListParts",
                 "name/cos:UploadPart", "name/cos:CompleteMultipartUpload",
                 "name/cos:AbortMultipartUpload"],
      "resource": ["qcs::cos:ap-hongkong:uid/1301304366:lhcos-36974-1301304366/rightwrite/*"] }
  ]
}
```

**故意不授予 `GetObject` 和 `DeleteObject`。** 服务器上的这把密钥只能往桶里写，**读不了已有备份、也删不掉**。这样即使服务器被入侵、密钥泄露，学生数据不会被读走，备份也毁不掉——备份是最后一道防线，能被同一把钥匙毁掉就不叫防线。

2026-09-08 实测验证：

| 操作 | 结果 |
|---|---|
| 上传 PutObject | ✅ 成功 |
| 列举 GetBucket | ✅ 成功 |
| 下载 GetObject | ❌ 403 拒绝 |
| 删除 DeleteObject | ❌ 403 拒绝，对象完好 |

**代价**：真要恢复数据时，需从控制台手动下载备份文件，或临时给该策略加 `GetObject`。恢复是低频操作，值得。

**MFA 说明**：该子用户的「登录保护」因主账号全局策略无法关闭，但它只作用于控制台登录，对纯编程访问的用户是空转，无影响。「操作保护」**必须关闭**——该用户永远登不进控制台、绑不了 MFA 设备，一旦触发校验就是无解失败。

### 更换密钥

```bash
# 1. 控制台禁用旧密钥、新建密钥
# 2. 把 /opt/rightwrite/.cos.yaml 里的 secretid / secretkey 两行改掉（600 权限，属主 rightwrite）
# 3. 验证
sudo -u rightwrite bash -c 'cd /opt/rightwrite && HOME=/opt/rightwrite \
    coscli ls cos://backup -c /opt/rightwrite/.cos.yaml'
sudo systemctl start rightwrite-backup
```

**踩坑记录**：coscli 会在**当前工作目录**写日志，systemd 服务默认 cwd 是 `/`，`rightwrite` 无写权限会报 `mkdir .: permission denied`。`offsite.sh` 里已 `cd /opt/rightwrite` 并设 `HOME` 规避——手动跑 coscli 时同样要注意。

零配置的补充方案：控制台手动打**系统盘快照**，或开启定期快照策略。
